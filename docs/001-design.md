## 1. 问题定性：两类失败，分开治

| | 遵循损耗 | 能力边界 |
|---|---|---|
| 本质 | 会做但没做 | 做不到 / 做不准 |
| 典型 | 没打开清单就宣称审了；用例没覆盖完就派开发；跳步；忘记回看 execution-playbook | "这个设计有没有架构隐患"判断错；"需求目的能不能达"判断错 |
| 判据 | 给它干净上下文、刚读完规范，它能做对 | 给它干净上下文也做不对 |
| 解法 | **机制**（门禁、schema、工作流、常驻提示） | 换更强模型 / 拆小判断 / 人兜底 |
| 机制的作用 | 根治（在可机检范围内） | **零** |

**你当前最大的痛（"我得不停提醒它再看一下 skill"）全部属于遵循损耗。** 能被提醒修好的，都是这一类。

### 4.1 环境与权限矩阵（未实现，依赖实体准备）

**状态：未实现。** 本仓没有任何代码按阶段注入凭据，也没有环境探测；这一节是**目标形态**，不是当前行为。落地前提是 §11 的实体准备。

```
              测试环境                     生产环境
数据库        读写全权                     读：只读账号（常开）
                                          写：令牌门
服务器        shell 全权                   读日志：只读账号（常开）
                                          变更：令牌门
相关组件      全权                         按需，令牌门
流水线        可触发                       令牌门
```

**生产不是"全锁"，是"读常开、写令牌"。**

| 能力 | 凭据 | 要令牌吗 |
|---|---|---|
| 查应用日志 / nginx / journalctl | 只读账号 | 否 |
| 库查询（SELECT） | 只读 DB 账号 | 否 |
| 探活、只读接口巡检 | 无 | 否 |
| 本批 DDL / DML | 写账号 | **是** |
| 触发生产流水线 | 流水线 token | **是** |
| 回滚 | 写账号 | **是**（同一次令牌覆盖） |

- **全权是前提，不是妥协**：测试环境不给全权，E2E 验数据、造夹具、重启服务都做不了，"全栈研发"就是空话。
- **两个维度**：角色决定"能做什么动作"（静态 8 个 preset，见 §4.4），环境决定"对谁做"（动态：由状态机阶段注入凭据）。不因此膨胀成 16 个 preset。
- **凭据不进 skill**：skill 是知识，凭据是动作的前置条件，只由阶段注入。
- **测试全权 + 留痕**：写操作必须 SQL 归档到需求目录；改数前备份、先 select 后 update。缺归档或备份 → 写操作脚本拒绝执行。
- **破坏性操作垫片**：`drop` / `truncate` / `rm -rf` 一类走二次确认垫片——不禁止，但留痕，防手滑与被注入。

### 4.2 只读账号（未实现，依赖实体准备）

**状态：未实现。** 本仓没有只读数据库账号，也没有受限 shell 账号；没有任何门禁在读它们。

- **只读必须是账号级的只读**：靠 `GRANT SELECT` 和受限 shell 账号保证，**不能靠门禁过滤 SQL 关键字**——agent 能拼字符串绕过去，账号权限绕不过去。这是"能用只读账号就用只读"的落地形态。
- 需要建的是两个实体：数据库只读账号（`GRANT SELECT`）、服务器受限 shell 账号（只能看日志、探活）。没有这两个账号，"读常开"就是空话。
- 验证标准不是文档自证，而是**用只读账号执行一次写操作并失败**。

### 4.3 生产令牌：一次性批次文件（未实现，依赖实体准备）

**状态：未实现。** `~/.dsh/prod-authorizations/` 尚未建立，校验与消费逻辑不在本仓代码里。语义定版于用户 2026-11-03：

| 项 | 规定 |
|---|---|
| **位置** | `~/.dsh/prod-authorizations/`，**仓库外**；目录权限保证 **agent 只读、人只写** |
| **命名** | `<批次号>.auth`，批次号与需求编号一致（如 `REQ-58`） |
| **内容** | 批次号 / 授权范围（`sql`、`pipeline`、`rollback` 的子集）/ 授权人 / 授权时间 / 本批 SQL 文件清单 + 内容 hash |
| **消费** | 生产阶段开头校验 → 原子改名归档到 `consumed/` → **同一文件不能二次使用** |
| **校验** | 批次号匹配 + 范围覆盖所需动作 + 未消费 + SQL hash 与实际要执行的一致 |
| **失败** | 任一项不符 → 生产阶段不执行，报「缺授权：<具体哪项>」 |
| **归档** | `consumed/` 永久保留，事后可追「谁批的、批了什么、什么时候用的」 |

**一句话令牌**：一句"上线" = 一次性令牌，覆盖**本批 SQL 执行 + 流水线触发 + 回滚**三件事，只对当批有效，不跨批顺延，不落配置。

**为什么绑定 SQL hash**：防"批了 A 却执行 B"。授权对象是**内容**，不是动作。

**为什么放在仓库外**：如果 agent 能写令牌文件，这道门就是假的。目录权限必须让它只能读——**门禁的可信度取决于它读的那个东西不在被管对象的写范围内**。

**回滚的处置**：同一批次号的令牌覆盖回滚，允许发布失败后立即回滚；但回滚必须留痕 + 事后报告（回了什么、为什么、回到哪个版本）。

### 4.4 角色清单（设计与开发分离）——已实现

本节已落地：`roles/*.role.yml` 是 8 个角色 manifest，`node scripts/roles.mjs --write` 生成 `presets/roles.patch.yml`（安装形态用 `--out <path>` 写到 profile 侧，包目录只读）；`node scripts/install-presets.mjs` 负责生成→备份→合入 profile→校验→提示重启。角色是数据，代码里不写死角色。

| 角色 | 干什么 | 能写什么 | 明确不做 |
|---|---|---|---|
| **主 PM** | 整体方案、拆解、裁决、验收、git 提交 | 文档 / 契约 / 提交 | 不写业务代码 |
| **后端设计** | 局部设计：接口、模块、表结构、状态机 | docs（design / api-contract / 流程节点） | 不写实现代码 |
| **后端开发** | 按冻结的 design + 契约实现 | 后端源码 + 回填文档 | 不改契约、不写单测 |
| **前端开发** | 按契约先写页面（mock），后端可用后对接 | 前端源码 + 回填文档 | 不改后端、不改契约 |
| **移动端开发** | Flutter / uni-app 各轨实现 | 该端源码 | 同上 |
| **插件开发** | 按冻结设计实现 DSH bundle / 宿主插件（TypeScript） | 插件源码、脚本、测试 | 不改契约、不写 README 口径 |
| **测试** | 端到端：前端入口→后端→连库验数据；用例集与覆盖评审 | 测试用例 / 报告（不改业务代码） | 不写业务代码，只测和报 |
| **运维** | 发版、日志定位、异常处置、生产只读排查 | 执行脚本 / 运维记录 | 不改业务逻辑 |

**设计与开发分离的意义**：设计角色**没有写源码的权限**，开发角色**没有改契约的权限**。两边写范围不重叠，这正好落在文件版本守卫和 preset 工具集上——不是靠"请不要"，而是靠"做不到"。

**主 PM 与后端设计的分工**（依据 skill 2026-09-30 定版）：整体方案、拆分维度、架构形态由**主 PM 自己定**；局部设计（某个接口、某个模块）**派给后端设计通道**；局部设计产出后主 PM **逐个审查、拼装成整体方案**——禁止整包外包。

## 5. 状态机：六阶段 + 回边 + 失败类型

你的流程不是线性的，是带回环的状态机。每条回边有**类型**、有**预算**、有**去向**。

```
 澄清 ──[七件不齐 / 目的不可达]──────────→ 回需求方
   │
   ▼
 设计 ──[设计审查门不过]──────────────────┐
   │                                      │
   ▼                                      │
 开发（前后端并行 + 测试同批）             │
   │──[DESIGN_UNFEASIBLE 开发报不可实现]──┤   ← 无产物打回，回设计
   │──[CONTRACT_GAP 契约缺口]─────────────┤
   │──[CONTRACT_CONFLICT 两端理解不一致]──┤   ← 主 PM 裁决
   ▼                                      │
 开发完成 ──[IMPL_MISMATCH 审查打回]───────┘
   │
   ▼
 测试（E2E）──[TEST_FAIL 归因]──→ 回对应通道
   │
   ▼
 验收（含评审检查）──[ACCEPT_P0 阻断]──→ 回开发 + 补用例
   │                ──[ACCEPT_P1P2]──→ 合并成一批，一轮修一轮回归
   ▼
 上线（收尾并入本阶段：worktree 清理 / 云效状态 / 文档盘点）
   │──[部署假绿 / INCIDENT]──→ hotfix 旁路（无预算，人上报）
```

### 失败类型 → 回边 → 预算

**裁决权全部在主 PM**（skill 已定版：主 Agent 是最终把关人、唯一对用户的接口；子 Agent 排查只带事实不带判断，根因判定/架构裁决/修复方案由主 Agent 做出）。代码和测试只负责**检测事实**，不负责决定去哪。

| 失败类型 | 代码失败类型 | 检测者（只给事实） | 回边去向（主 PM 裁决） | 预算（按阶段） |
|---|---|---|---|---|
| 需求要素不齐 | 门禁拒绝、无预算 | 门禁：七件缺项清单 | 回需求方 | 无限（外部） |
| 目的不可达 | 门禁拒绝、无预算 | 澄清会话：推演结论 + 依据 | 回需求方重新定义 / 上报 | 一次后上报 |
| 设计审查不过 | 门禁拒绝、无预算 | 门禁筛结构 + 主 PM 审内容 | 回设计 | 2 次 |
| DESIGN_UNFEASIBLE | `DESIGN_UNFEASIBLE` | 开发：不可实现的位置与理由 | 回设计改方案 / 打回开发 | 2 次 |
| CONTRACT_GAP | `CONTRACT_GAP` | 开发：缺哪个端点/字段 | 回设计补契约 | 3 次 |
| CONTRACT_CONFLICT | `CONTRACT_CONFLICT` | 测试：两端行为差异实证 | 主 PM 判契约是否有歧义 | 1 次（再不行上报） |
| IMPL_MISMATCH | `IMPL_MISMATCH` | 门禁：清单逐条对比结果 | 回开发 | 1 次打回 / 2 次拆小 / 3 次上报 |
| TEST_FAIL | `TEST_FAIL` | 测试：用例失败 + 归因事实 | 回开发或回测试 | 同上 |
| ACCEPT_P0 | `ACCEPT_P0` | 主 PM 亲验 | 回开发 + 补用例 | 3 次后上报 |
| 部署假绿 | 无代码枚举，无预算 | 人：探活断言 | 回上线 / hotfix | 无预算，人上报 |

**6 个代码失败类型**：`devflow_state.rework` 只接受 `DESIGN_UNFEASIBLE`、`CONTRACT_GAP`、`CONTRACT_CONFLICT`、`IMPL_MISMATCH`、`TEST_FAIL`、`ACCEPT_P0`。预算按阶段重置（进入新阶段即清零），耗尽后 `advance` 在该阶段被拒绝，即使门禁本身通过。表里「需求要素不齐」「目的不可达」「设计审查不过」是门禁拒绝，不占预算；「部署假绿」没有 `ship` 门，由人在该阶段发现并上报，因此没有对应枚举。

**三段分工**：门禁判"够不够格进下一步"（代码）；测试与各角色只报"事实与证据"（不带判断）；**去哪修、信谁、要不要上报——全由主 PM 裁决**（模型）。

## 6. 四道阶段门 + 一项附加检查的产物契约

| 门 | 阶段 | 产物 | 代码能判（硬） | 只能模型判（软） |
|---|---|---|---|---|
| 需求澄清冻结 | `clarify` | `requirement.md` 七件 + `assessment.md` | 七件齐否；待问/冲突清单是否清零；FP 每条有原话依据 | 目的可达性推演对不对 |
| 设计审查前置门 | `design` | `design.md` + `api-contract.md` | 横切面五项齐否；FP×设计章节矩阵有无空行；契约字段完整 | 架构形态合不合理 |
| 用例评审门 | `test` | `test-cases.md` + `test-report.md` | 每个 FP 有用例；无孤儿用例；每条有验证层与优先级；执行报告存在且非空壳 | 用例测得对不对 |
| 最终审查（附加检查，在 accept 内执行） | `accept` | `review-notes.md` | 完整清单 115 条由人/技能执行，机检下限 30 条逐条有 verdict + `路径:行号` 证据，且证据在 root 内可解析 | 结论对不对 |
| 双闸验收 | `accept` | `acceptance-report.md` + `ui-acceptance.md`（或在配置中显式豁免） | 剧本每环有结论；逐 FP 有结论且挂证据；P0 清零；界面产物齐备或豁免有理由 | 体验好不好 |

build 与 ship 不设门：build 只承载状态，ship 的收尾动作与部署假绿由人在该阶段发现并上报（无预算）。

**三层防线**：结构（schema）→ 业务约束（门禁纯函数）→ 证据真实性（带工具校验会话）。

## 7. 角色归属与硬挂

```
全局池  ~/.agents/skills/         L0 总路由 + L1 关卡 + 通用审查基线   → 所有角色
角色池  各 preset 绑定             L2 能力闸 + 该角色专用知识          → 只有该角色
项目池  <仓>/.agents/skills/       该仓 project-standard 衍生件        → 进这仓的角色
```

**硬挂的本质**：preset 决定**包技能**的可见集合。挂了三个 pack 技能，就只有这三个 pack 技能出现在该角色的会话里，其余 pack 技能物理上不存在。**内置技能不适用**：`skills/` 随 bundle 发布的技能由唯一一条全局条目广播，是全员公共核心——`include` 只缩本实例视图，`exclude` 在会话层面对它们无效（注册表按技能名合并，近层只能遮蔽同名，不能删除）。这条隔离语义已定版，写法见 `docs/002-role-presets.md`。

**必须配的兜底**：角色不知道自己没有哪些 pack 能力。所以每个 preset 的系统提示词里必须有——
> 需要的能力不在你的装备清单内时，停下来上报，不要自行替代。

**权限靠工具兜底，不靠文档**：只读诊断类 skill 全员挂；生产写操作类只有运维通道有工具。

### 7.1 文档契约：skill 写死"有哪些、怎么落"，不写内容

铁律：**skill 里不出现任何项目逻辑**（技术栈、表名、接口路径、页面模板、SQL 示例），只写"必须存在哪些文档、必须含哪些章节、谁在哪一步建、缺了怎么判"。

每个 skill 附带一张**文档契约表**：

| 文档 | 位置 | 必含章节 | 谁建 | 何时更新 | 怎么校验 |
|---|---|---|---|---|---|
| 全局业务文档 | `<后端仓>/docs/` | 业务架构 / 业务流程 / 术语表 / 角色权责矩阵 | 主 PM | 每轮盘点 | 章节存在 + 术语增量 |
| 项目规范 | `<仓>/docs/dev/project-standard.md` | 9 个固定章节 | init 子会话起草、主 PM 审定 | 每轮沉淀专项条目 | 章节存在 + 禁"待补"超期 |
| 需求目录 | `<后端仓>/docs/dev/<NNN-slug>/` | 七件 + assessment + review-notes + execution-plan | 各阶段产出者 | 随阶段推进 | 逐件 schema 校验 |
| 项目清单 | `<仓>/docs/dev/project-manifest.md` | 端类型 / 角色集 / 门禁变体 / 依赖方向 | 新仓首建 | 立项或角色变化 | 角色名必须在静态库里 |

**"如何落"四件事必须写死在 skill 里**（这是 skill 该管的，不是项目该管的）：

1. **缺则建**：首次进入某仓时文档缺失 → 按端类型模板生成骨架 → 主 PM 审定后落盘 → 未经审定不算存在
2. **每轮盘点**：迭代收尾五类各填，或显式写"本轮无新增"——写不出就不给交付汇报
3. **旧则立碑**：被替代的文档挂墓碑（停维护日期 + 原因 + 替代者），不删文件，保可追溯
4. **差则打回**：超期未核对、有替代未挂墓碑、changelog 混进入口件 → 门禁直接打回

### 7.2 项目装配：零件静态，组合动态

```
                 设计  后端   web   mobile   test   ops
后端 service-a  ✅    ✅                   ✅     ✅
PC 端 ×3                ✅     ✅            ✅
H5 /m/                  ✅     ✅            ✅
Flutter App                          ✅      ✅
桌面工作台              ✅     ✅            ✅
```

- **横轴静态**：8 个角色 preset（主 PM / 后端设计 / 后端开发 / web / 移动端 / 插件开发 / 测试 / 运维），写一次
- **纵轴动态**：每个仓的 `project-manifest.md` 声明启用哪几个角色
- **格子的内容** = preset 装备 + 该仓 `.agents/skills/`（按会话工作目录自动发现，优先级高于全局池，零配置）
- **设计通道的位置**：跨端共用一份 `design.md` + `api-contract.md`（落在后端仓），所有端的开发都引它；页面设计节也在同一份里，由前端/移动端照稿实现
- **默认值**：没有 manifest 的仓 → 最小集（设计 + 后端 + 测试）；声明才扩，不声明不膨胀
- **边界**：不允许运行时生成 preset——只能从静态零件库里选。否则"角色装备"又变成模型现场决定的东西，漂移回来了

## 8. 团队方案评估：为什么暂不采用

（详见对话：Lead 存在、文件共享/对话不共享、点对点消息、任务板）

结论：
- 团队解决的是**并发协作与长驻**，不是**角色隔离与流程遵循**
- 缺 per-member preset → 硬挂做不到
- 成员工具集相同 → 越界拦不住（写范围明确写着 advisory）
- 允许 peer 直聊 → 与"决策上报制"冲突
- Lead 仍是会话，仍要记得流程 → 不治漂移

### 8.1 可吸收清单（逐条核过源码）

| 团队机制 | 源码位置 | 能不能拿 | 怎么拿 | 代价 |
|---|---|---|---|---|
| 文件版本守卫（FS_STALE_VERSION） | `dsh-fs-local` writeText 的 `replaceIfVersion` | ✅ **已经免费拥有** | 无需动作，它是 fs 工具的全局策略，不是团队专属 | 无 |
| 读后写（FS_NOT_OBSERVED） | 同上 `createIfAbsent` | ✅ 已有 | 同上，文件必须先读才能覆盖 | 无 |
| 任务板结构（revision / blockedBy / writeScopes / owner） | team 包 `teamTaskSnapshotSchema` | ⚠️ 半拿 | 用文件承载（`execution-plan.md` 已经是任务账）+ 门禁校验字段 | 低；失去原子 claim，但单进程不需要 |
| readiness 自动调度 | `taskReady()` | ❌ 不需要 | 团队本身也不自动派（"Task readiness never starts an owner"） | — |
| 长驻成员 / 可唤醒 | member phase + 持久收件箱 | ❌ 拿不到 | C 方案用"多次派单"替代 | 任务书必须自包含（现有五段模板已满足） |
| 成员互发消息 | `send_message` 可指定 teammate | ❌ 不该拿 | 与"决策上报制"冲突 | — |

**结论**：团队里最值钱的两样——文件版本守卫、任务板结构——**一样是全局已有的，另一样可以降级成文件**。真正团队独有的只有"长驻成员"，而你的流程是"派单→交付→收编"，不需要长驻。**不接团队，也能把优点吃掉。**

**守卫的边界**：它只管 `write`/`edit` 工具，**不管 bash**（团队策略原文：Bash, formatters, code generators 不受版本守卫保护）。所以 git 操作、构建脚本仍可能互踩，这一块仍需"禁重启窗口 + 文件不相交"的人工约定兜底。
