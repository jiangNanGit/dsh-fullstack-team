# 角色初始化

角色是可插拔的，只有主智能体是固定的。本规程规定主智能体如何把一个陌生仓库装配成一支能开工的队伍。

## 一、侦查：只认证据，不认印象

读仓库根目录的标记文件，命中即判定技术栈：

| 标记文件 | 角色 id |
| --- | --- |
| `pom.xml` / `build.gradle` / `build.gradle.kts` | `backend-java` |
| `package.json` + `vite.config.*` | `frontend-vue` |
| `pubspec.yaml` | `mobile-flutter` |

**唯一事实来源是本插件 `roles/*.role.yml` 里的 `detect` 字段**，不是这张表。表是给人看的速查，判断时以 manifest 为准；manifest 新增了角色，无需改本 skill。

一个仓库命中多个标记，就装多个角色（后端 + 前端同仓很常见）。

**没有任何命中**：不要猜。先看 README、构建脚本、CI 配置；仍然无法判定，向用户报告"未识别技术栈"，列出你查过的文件。猜错的代价是整轮用错技能。

## 二、定角色：core 恒装，stack 按命中

- **core 角色**（`pm` / `backend-design` / `qa` / `ops`）：每个项目都要，直接装。
- **stack 角色**（`backend-java` / `frontend-vue` / `mobile-flutter`）：命中才装，没命中不装。

## 三、校验装备：先算能不能装，再装

运行：

```bash
node scripts/roles.mjs
```

输出会列出每个角色能不能装配；缺包的会给出缺失目录和获取提示。**不要跳过这一步直接装配**——缺包的角色会被插件拒绝启动，而不是降级运行。

## 四、缺技能：四级处置，逐级下沉

严格按顺序，前一级拿不到才走下一级：

1. **预置**：本插件 `skills/` 已带——直接用。
2. **已有包**：`~/.dsh/skill-packs/<name>/` 已存在，或项目 `.agents/skills` 里已有——直接挂。
3. **可获取**：用插件市场或 npm 搜索该能力（关键词如 `flutter skill`、`dsh flutter`）；找到后请用户确认安装，装完重跑 `node scripts/roles.mjs --write`。
4. **拿不到**：**降级并上报**——明确告诉用户"这个角色缺 X 能力，我按不含 X 的方式开工"，列出缺失带来的具体风险。禁止假装具备。

## 五、落地：写进配置，不写进项目

角色装配结果落两处之一：

- 生成 `presets/roles.patch.yml` 并合入 `~/.dsh/profiles/<profile>/cordis.patch.yml`（可复用，跨会话）
- 或者只在本次会话内以任务书形式声明角色分工（一次性）

**禁止**把角色技能复制进项目仓库。同一个技能出现两份副本，等于埋下一个"哪份才是真的"的隐患。

## 六、禁止项

- 禁止凭印象判断技术栈（必须读文件）
- 禁止为缺失技能临时编造替代流程
- 禁止把角色技能副本写进项目
- 禁止把 stack 角色全量预装（没命中就不装，装了只是噪音）
