# 角色初始化与角色创造

角色是可插拔的，只有主智能体固定。本规程规定主智能体如何把一个仓库装配成一支能开工的队伍，以及**装配不出时如何按设计理念把缺的一环造出来**。

## 一、侦查：只认证据

读仓库根目录标记文件，命中即判定技术栈：

| 标记文件 | 角色 id |
| --- | --- |
| `pom.xml` / `build.gradle` / `build.gradle.kts` | `backend-java` |
| `package.json` + `vite.config.*` | `frontend-vue` |
| `pubspec.yaml` | `mobile-flutter` |

**唯一事实来源是本插件 `roles/*.role.yml` 的 `detect` 字段**，表只是给人看的速查。manifest 新增角色，本 skill 无需修改。

一个仓库命中多个 → 装多个角色。没有任何命中 → **不要猜，也不要停**：继续看 README、构建脚本、CI 配置、目录结构，直到能判定技术栈；判不出来就走第五节的「创造」——先造一个能识别它的角色。

## 二、定角色：core 恒装，stack 按命中

- **core**（`pm` / `backend-design` / `qa` / `ops`）：每个项目都装
- **stack**（`backend-java` / `frontend-vue` / `mobile-flutter`）：命中才装

## 三、校验装备：先算，再装

```bash
node scripts/roles.mjs          # 报告：谁能装、谁缺什么、缺的在哪
node scripts/roles.mjs --write  # 生成 presets/roles.patch.yml
```

缺包的角色**会被插件拒绝启动**，不会降级运行。所以先算清楚再装。

## 四、缺能力：五级处置，逐级下沉

严格按顺序，前一级拿不到才走下一级：

1. **预置** —— 本插件 `skills/` 已带，直接用
2. **已有** —— `~/.dsh/skill-packs/<name>/` 或项目 `.agents/skills` 里已有，直接挂
3. **可安装** —— 用插件市场或 npm 搜到（关键词如 `flutter skill`、`dsh flutter`），请用户确认后安装，装完重跑 `--write`
4. **可检索** —— 全网搜索该能力的官方文档、社区技能包、最佳实践；评估后安装，或据此提炼技能内容
5. **创造** —— 上面都没有，就按设计规范造一个

只有一种情况才允许上报降级：能力本身依赖你拿不到的东西（生产库凭证、第三方账号、真实设备）。此时明确说出"缺 X、因此不做 Y、风险是 Z"，禁止假装具备。

## 五、创造：换形态拆角色，换知识写技能

先判定缺的东西属于哪一层——**判错层比不造更糟**：

| 变化点 | 归属 | 动作 |
| --- | --- | --- |
| 换输入形态或输出口径（谁来干、交出什么） | **角色** | 新增 `roles/<id>.role.yml` |
| 换领域知识或执行标准（怎么干、判据是什么） | **技能** | 新增 `skills/<能力名>/SKILL.md` 或 skills 包 |
| 换外部系统或工具（查库、调接口） | **工具/MCP** | 接工具，不写成技能 |

判定口诀：**换形态拆角色，换知识写技能，换系统接工具。**

### 造角色：三步

```bash
node scripts/roles.mjs new backend-go --name "后端开发（Go）"
```

1. **定 `kind`**：跟流程走、每个项目都要 → `core`；跟技术栈走 → `stack`
2. **定 `detect`**：该项目出现哪些文件就该装这个角色（`go.mod`、`Cargo.toml`……）
3. **定 `contract`**：输入什么、交出什么。这是角色的**接口约定**，不是流程说明

```yaml
id: backend-go
kind: stack
detect: [go.mod]
include: [dev-orchestrator, requirement-clarify, acceptance-guard]
contract:
  input: design.md + api-contract.md + 任务书
  output: 可编译代码与自测结果
```

`include` 就是**代码层写死的技能清单**：挂哪些能力由这一行决定，角色运行时枚举不到的就是不存在。不要靠提示词让模型自己挑技能。

### 造技能：四条硬标准

1. **能力命名 = 动词 + 领域**（`api-contract-review`、`flutter-layout-audit`），**禁止场景名**（`某企业下单需求`、"模式二"这类业务流程名）
2. **复用性检验**：换一个业务场景，这份 SKILL.md 一字不改还能用吗？能 = 能力定义；不能 = 写成了场景说明书，回去重构
3. **不写项目逻辑**：不写栈、不写表名、不写接口路径、不写页面模板。项目知识留在项目里
4. **不写输入输出契约**：契约是角色的职责，技能只写"怎么做这件事"与判据

技能里该硬写的是：**规范文档有哪些、必须包含哪些章节、谁负责产出、什么时候刷新、违规怎么发现**。

### 造完必须验证

```bash
node scripts/roles.mjs --write     # 角色能装配
pnpm test                          # 清单与渲染没被写坏
```

## 六、落地：写进配置，不写进项目

装配结果落两处之一：生成 `presets/roles.patch.yml` 合入 profile 的 `cordis.patch.yml`（跨会话复用），或本次会话内以任务书声明分工（一次性）。

**禁止**把角色技能复制进项目仓库——同一个技能出现两份副本，等于埋下一个"哪份才是真的"的隐患。

## 七、反模式（自查用）

- ❌ 一个角色挂多个任务形态的技能全集，靠提示词路由
- ❌ 技能按业务场景命名、内容绑死单一业务
- ❌ 把外部系统调用写进 SKILL.md（那是工具层）
- ❌ 缺能力时假装具备，或用临时编造的流程顶替
- ❌ 把角色技能副本写进项目
- ❌ stack 角色全量预装（没命中就不装，装了只是噪音）
